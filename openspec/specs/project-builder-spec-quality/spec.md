## Requirements
### Requirement: Canonical rich Builder spec contract
Every detailed spec generated by Project Builder SHALL contain a `kind` (`scaffold|feature|verification`), an English action-oriented title, a one-sentence `shortSummary` no longer than 240 characters, a `description` with exactly the five canonical named sections `## Problem Statement`, `## Proposed Solution`, `## Out of Scope`, `## Technical Considerations`, and `## Estimated Complexity` in that order, a separate `acceptanceCriteria` array containing 4–10 non-empty testable outcomes, a valid `priority`, labels, and an optional dependency on an earlier spec. `Out of Scope` and `Technical Considerations` SHALL each contain at least 2 bullets. The description SHALL NOT duplicate an `## Acceptance Criteria` section.

#### Scenario: Complete rich spec
- **WHEN** the Builder produces a detailed spec
- **THEN** its description explains the user problem, concrete solution, deliberate exclusions, technical constraints, and justified complexity, while its separate criteria cover independently verifiable outcomes

#### Scenario: Criteria are not duplicated
- **WHEN** a generated spec is materialized as a Board ticket
- **THEN** one deterministic `## Acceptance Criteria` section is folded into the stored description from the structured array

### Requirement: Phase-appropriate technical grounding
Day-0 M1 specs SHALL reference the selected stack, planned components, contracts, risks, and inter-spec dependencies without inventing repository paths. M2+ specs SHALL be grounded by reading the real project and SHALL name only existing paths and identifiers that were verified during generation.

#### Scenario: Day-0 scaffold has truthful context
- **WHEN** the first M1 spec describes project scaffolding before a repository exists
- **THEN** it names the chosen stack, notes that the repository already contains a README, defines run/test/CI outcomes, and does not claim unverifiable file paths

#### Scenario: M2 uses the real codebase
- **WHEN** a later milestone is generated for an existing project
- **THEN** its technical considerations refer to verified code locations and adapt the planned titles to the implementation that actually exists

### Requirement: Backward-compatible blueprint schema
The version-1 blueprint SHALL preserve `specsComplete` and each detailed spec's `kind`, `shortSummary`, `acceptanceCriteria`, and `priority` through server parsing, client parsing, and full-snapshot streaming. Day-0/M1 workspace persistence SHALL retain those values in `m1Specs`; M2+ detailed persistence SHALL use the created tickets because the version-1 milestone schema has no detailed-per-milestone collection. Readers SHALL default a missing completion flag to false, kind to `feature`, short summary to empty, criteria array to empty, and missing/invalid priority to `medium` so previously persisted blueprints remain readable. Live parsing SHALL also retain the exact pre-normalization JSON for readiness and commit, while server `readBlueprint` SHALL normalize legacy persisted JSON.

#### Scenario: New rich fields round-trip
- **WHEN** a valid `blueprint-draft` contains criteria and priority
- **THEN** the live panel retains those values, M1 `blueprint.json` retains them, and an M2+ commit retains them in the authoritative created tickets

#### Scenario: Legacy blueprint remains readable
- **WHEN** a version-1 blueprint created before this change omits the new fields
- **THEN** both parsers accept it with empty criteria and medium priority rather than rejecting the snapshot

#### Scenario: Raw generated payload survives compatibility parsing
- **WHEN** a generated block contains a value that compatibility normalization would default or drop
- **THEN** the UI may render the normalized view, but readiness and commit still inspect the exact raw value and reject it when invalid

### Requirement: Quality gate before mutation
The day-0 project commit and M2+ milestone commit SHALL require `specsComplete=true` and validate every detailed spec's exact raw generated fields with one shared deterministic quality contract before mutating the filesystem, project registry, blueprint, or ticket store. Validation SHALL reject an M1 set outside 5–10 specs; missing, duplicate, empty, or out-of-order canonical sections; fewer than 2 bullets in either Out of Scope or Technical Considerations; criteria outside the 4–10 range; invalid priority/kind; a missing first M1 scaffold; and dependencies that do not point to an earlier spec. Compatibility defaults or dropped fields SHALL NOT make invalid generated JSON pass. A rejection SHALL identify the failing spec and field.

#### Scenario: Poor M1 draft cannot create a project
- **WHEN** any M1 spec contains only summary prose or lacks required structured content
- **THEN** the project commit returns a named validation error before creating the target directory

#### Scenario: Poor M2 batch is atomic
- **WHEN** any generated M2 spec fails quality validation
- **THEN** the milestone endpoint returns 400, inserts no tickets, and leaves the milestone status unchanged

#### Scenario: Dependency points forward
- **WHEN** a spec depends on itself or a later spec index
- **THEN** validation rejects the complete set rather than silently dropping the prerequisite

#### Scenario: Invalid enum cannot default into validity
- **WHEN** raw generated JSON contains an unsupported priority or kind
- **THEN** readiness stays false and the server rejects the commit instead of accepting the normalized default

#### Scenario: Partial generation is not committable
- **WHEN** a snapshot contains generated specs but `specsComplete` is false
- **THEN** the UI keeps commit disabled, the server rejects a crafted commit request, and the normal generation flow never presents it as the completed result

### Requirement: Blueprint approval precedes detailed generation
Interview and “surprise me” turns SHALL fill product, flow, platform, stack, assumptions, and milestones while keeping `m1Specs` empty and `specsComplete=false`. Only explicit user approval or a direct request to generate the backlog SHALL produce detailed M1 specs. The next assistant response SHALL contain ONE full snapshot with the entire self-validated 5–10-spec M1 set and `specsComplete=true`; the agent SHALL NOT emit closed partial 2–3-spec snapshots or leave a subset as commit-ready state.

#### Scenario: Surprise me does not create placeholders
- **WHEN** the user asks the Builder to decide the initial blueprint
- **THEN** the response proposes all blueprint dimensions but contains no shallow detailed specs and invites approval before generation

#### Scenario: Approved blueprint produces final batch
- **WHEN** the user approves the proposed blueprint and asks for specs
- **THEN** that single response emits one full snapshot containing the complete rich M1 set and marks it complete only when every spec satisfies the quality contract

### Requirement: Provider-equivalent read-only milestone generation
The complete dynamic M2+ grounding and rich-spec contract SHALL reach Claude, Codex, and Gemini, including the rule that every detailed spec for the target milestone must be returned in one assistant response and one complete snapshot. When a provider does not support a dedicated system-prompt argument, the server SHALL include the milestone instructions and blueprint context in the effective user turn. The prompt SHALL forbid mutation, write-capable commands/tools, builds, and tests, and SHALL identify the real source repository for relocated projects. Native policy SHALL give Claude plan/safe mode with only Read/Grep/Glob, Codex a read-only filesystem sandbox, and Gemini plan mode without yolo. Gemini's boundary SHALL be represented as policy-layer because its CLI exposes no selectable filesystem sandbox; incompatible safety flags SHALL fail closed rather than fall back to yolo.

#### Scenario: Codex receives M2 contract
- **WHEN** an M2 conversation uses Codex
- **THEN** the invoked prompt contains the canonical headings, structured fields, one-response complete-set rule, completion rule, and current blueprint context, and the invocation uses the read-only sandbox

#### Scenario: Claude and Gemini stay inspection-only
- **WHEN** an M2 conversation uses Claude or Gemini
- **THEN** Claude exposes only Read/Grep/Glob in plan/safe mode, while Gemini uses plan without yolo and is not described as having a filesystem sandbox

#### Scenario: Relocated grounding uses the source repository
- **WHEN** the project source is relocated outside the artifact workspace
- **THEN** the milestone prompt names the actual source path and `./project` mount so inspection does not target the empty workspace

### Requirement: Rich ticket persistence parity
Both M1 and M2+ materialization SHALL store the generated priority and short summary, fold structured acceptance criteria through the normal ticket-description helper, preserve domain labels plus the milestone label, and retain existing prerequisite/order behavior. The reviewed preview SHALL represent the same content that will appear in the Board ticket apart from that deterministic fold. M1 detail SHALL also remain in `blueprint.m1Specs`; for M2+, the created tickets SHALL be the authoritative detailed representation and the blueprint SHALL store only milestone status and advisory ticket IDs, with no invented detailed-M2 schema.

#### Scenario: M1 persists reviewed content
- **WHEN** a valid M1 blueprint is committed
- **THEN** each resulting ticket contains the five canonical description sections, one acceptance-criteria section, the generated priority, milestone/domain labels, and mapped prerequisites

#### Scenario: M2 matches M1 quality
- **WHEN** a valid grounded M2 batch is committed
- **THEN** its authoritative tickets use the same rich structure and ticket persistence rules as M1, while the blueprint milestone records only committed status and advisory IDs

### Requirement: Reviewable quality in the Builder UI
The Builder spec cards SHALL expose the short summary and number of acceptance criteria, and the detail modal SHALL render short summary, priority, the canonical description, and the criteria that will be folded into the final ticket. This preview SHALL work for both day-0 and later-milestone generation. Readiness SHALL use the raw payload rather than its normalized render model. After a successful later-milestone commit, the client SHALL refetch the blueprint and advance to the next milestone still planned.

#### Scenario: User reviews a generated spec
- **WHEN** the user opens a Builder spec card before commit
- **THEN** the modal shows all five description sections, priority, and every acceptance criterion without requiring the ticket to exist

#### Scenario: M2 commit refreshes the roadmap
- **WHEN** a reviewed M2 batch is committed successfully
- **THEN** the transient generation shell closes, the client refetches the blueprint, and the next Generate action targets the first later planned milestone

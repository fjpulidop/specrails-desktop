# Project Builder — greenfield project creation from an idea

## Why

Specrails today only serves repos that already exist: "+ Add Project" requires a path to an existing codebase, and every spec-creation surface (Explore, Quick, Jira, agent chat) assumes a project is already registered. Greenfield — where spec-driven development shines most — has no entry door. A user with just an idea must manually create a repo, scaffold it, import it, and only then start writing specs one by one. The Project Builder closes that gap: describe the app idea, get interviewed briefly, and receive a reviewed Milestone-1 backlog plus a bootstrapped repo, one click away from launching implementation rails.

## What Changes

- **"Existing | New" chooser** on "+ Add Project": a pre-screen with two cards. *Existing* → the current AddProjectDialog/setup wizard flow, byte-identical. *New* → the Project Builder.
- **Blueprint chat (day 0, app-level)**: a conversational Builder that runs WITHOUT a project (no project exists yet — sibling of the app-level agent-chat infrastructure, own system prompt, no MCP wiring). Interview discipline: ≤3 question turns, propose-don't-ask (agent proposes stack/scope with rationale, user corrects), a "surprise me" fast path that fills all dimensions with declared defaults, provider/model/reasoning-effort selection, and a live blueprint panel showing the 5 dimensions (product, core flow, platform, stack, M1 constraints) filling in as ✓/✗.
- **`blueprint-draft` fenced-JSON protocol**: single block type, full-snapshot / last-valid-wins (same mechanics as the existing spec-draft protocol). A valid block retains both a compatibility-normalized view for preview/read and its exact raw JSON for readiness and commit validation, preventing legacy defaults/drop rules from hiding invalid generated fields. The v1 snapshot also preserves `specsComplete`; every detailed spec preserves `kind`, one-sentence `shortSummary`, a canonical description, separate structured `acceptanceCriteria`, `priority`, domain labels, and an optional backward-only dependency. Existing persisted v1 snapshots remain readable because `readBlueprint` normalizes them server-side.
- **Approval before rich Milestone-1 generation (walking skeleton)**: interview and Surprise Me turns propose product/stack/milestones with `m1Specs: []` and `specsComplete: false`. Only explicit approval or a direct backlog-generation request starts detailed generation; the next assistant response contains the entire self-validated 5–10-spec M1 set in one full snapshot and sets `specsComplete: true`. The agent never publishes a 2–3-spec subset or leaves partial generation ready to commit; the first item is explicitly `kind='scaffold'`. Every detailed spec uses the normal Specrails contract: exactly `## Problem Statement`, `## Proposed Solution`, `## Out of Scope`, `## Technical Considerations`, `## Estimated Complexity` in order, with at least 2 bullets in each of Out of Scope and Technical Considerations, plus 4–10 acceptance criteria kept outside `description`, a one-sentence summary, priority, labels, and truthful phase-appropriate technical context. Day 0 references the planned stack but never invents file paths; the scaffold notes the repo already contains a README. M2+ milestones carry only high-level `plannedSpecs` titles until explicitly generated (anti-waterfall), then the target milestone's complete detailed set is likewise returned in one response/snapshot.
- **Single orchestrated commit** ("Create specs"): nothing touches disk before it. Mini-form (name prefilled from `product.name`, location default `~/projects/<slug>`, provider multi-select as in AddProjectDialog, optional "create private GitHub repo" checkbox gated on `gh` authenticated). A shared deterministic rich-spec validator gates both day-0 and later-milestone commits before any mutation and returns actionable spec/field detail. The day-0 streamed orchestration is: mkdir+validate → `git init -b main` + README generated from the pitch + initial commit → workspace assemble (prefer the bundled offline framework; fall back to `npx specrails-core` only in dev/non-desktop runtimes; a packaged desktop with a missing/corrupt bundle fails validation) → insert M1 tickets as `todo`, label `M1`, `source='project-builder'`, preserving generated priority/summary/domain labels and folding structured criteria once through the normal helper → write `blueprint.json` + `blueprint.md` → **register project last** (a mid-flight crash leaves an orphan dir, never a zombie half-project) → best-effort `gh repo create --private --source . --push` (failure = toast, never aborts).
- **Blueprint persistence in the workspace** (repo stays pristine): `<workspace>/.specrails/blueprint.json` (source of truth for the day-0/M1 snapshot and milestone roadmap/status machine `planned → committed → done`) + `blueprint.md` (deterministic render, never hand-edited). For committed M2+, the tickets—not a nonexistent detailed-per-milestone blueprint field—are authoritative for the reviewed descriptions/criteria/priority/summary/labels/prerequisites; the blueprint milestone retains only status and advisory `ticketIds`. Live truth for progress is always the ticket board (label `M<n>`), never stored ticket ids. The board also recognizes legacy Builder tickets recorded as `source='manual'` with `created_by='project-builder'`, so existing projects need no ticket-store migration.
- **"Launch Milestone 1" CTA**: the Builder's final screen offers launching ALL M1 tickets as ONE `batch-implement` rail (sequential, single worktree, single PR). Greenfield M1 specs are chain-dependent (scaffold → auth → model → core flow); parallel per-ticket rails from a near-empty `main` would each build on nothing. Batch = the correct shape; one milestone PR is expected to be large.
- **Sidebar re-entry + "Generate M2"**: a sidebar entry (visible in both board and mission modes) appears when `blueprint.json` exists, showing milestone progress and a "Generate M2" action. M2+ generation is a PROJECT-level, read-only inspection chat seeded with `blueprint.json`, the promised `plannedSpecs`, the canonical rich-spec contract, and grounding rules that require verified real paths/identifiers plus behavioral, failure/edge-case, and test coverage. The prompt forbids mutation/builds/tests and identifies the real source repo for relocated projects. Native policy maps Claude to plan + Read/Grep/Glob, Codex to its read-only sandbox, and Gemini to plan mode without yolo (Gemini has no selectable filesystem sandbox, so that boundary remains policy-layer and incompatible flags fail closed). The complete dynamic prompt reaches every provider and requires the entire target milestone set in one response/full snapshot. M2+ commit validates the raw batch, makes the inserted tickets authoritative for detailed content, records only status/IDs in the blueprint, then invalidates/refetches client blueprint state so the CTA advances to the next planned milestone.
- **Accounting**: day-0 Builder turns record into the existing app-level `agent_invocations` ledger (`project_id NULL` precedent); no backfill after project creation. M2+ turns record per-project as normal Explore turns.
- **Jira**: nothing special. Day 0 has no Jira; M2+ generation on a Jira-connected project rides the existing spec-creation → Jira machinery unchanged.

## Capabilities

### New Capabilities

- `project-builder-entry`: the Existing|New chooser on Add Project and the Builder shell UI (chat + live blueprint panel), including the "surprise me" path and interview discipline requirements.
- `blueprint-protocol`: the `blueprint-draft` fenced-JSON contract — schema (`blueprintVersion`, product, coreFlow, platform, stack, assumptions, milestones, `specsComplete`, rich `m1Specs`), snapshot semantics, approval-gated single-response complete generation, canonical spec quality, and the `blueprint.json`/`blueprint.md` persistence pair with the milestone status machine.
- `project-bootstrap-commit`: the single orchestrated commit — ordering, validation, README generation, offline workspace assemble, ticket insertion, register-project-last crash posture, optional GitHub remote creation, and the streamed progress UI.
- `milestone-lifecycle`: M1-only day-0 detailed generation rules (walking skeleton, approval-gated, scaffold-first, 5–10 cap), the "Launch Milestone 1" batch CTA, sidebar re-entry, board-derived progress, and "Generate M2" as provider-equivalent project-level grounded rich-spec generation.

## Impact

- **Client**: `AddProjectDialog` gains the pre-screen chooser; new Builder shell (chat left + blueprint panel right, ExploreSpecShell-inspired but project-less); new sidebar entry; commit mini-form + streamed orchestration view; new i18n namespace across all 8 locales.
- **Server**: new app-level `/api/blueprint/*` REST + a Builder chat manager (sibling of `AgentChatManager`, reuses `runAiCliInvocation`); blueprint-draft parser (adapting `spec-draft-parser.ts` mechanics); orchestrated-commit endpoint composing existing pieces (git init, `SetupManager` headless assemble, ticket store batch insert, project registration, `gh` via existing PATH resolution); blueprint render module (deterministic, `renderContractLayerMarkdown` pattern).
- **Reused unchanged**: batch-implement rail launch, safe-PR flow (local-only ladder covers no-remote projects), artifact relocation (pristine repo guaranteed), `agent_invocations` ledger, Jira outbox, setup prerequisites (gh auth signal).
- **Risk surface**: SetupManager coupling to the wizard flow (needs a headless assemble variant — verified as design-level, not a blocker); coverage thresholds require substantial tests for the new server modules.

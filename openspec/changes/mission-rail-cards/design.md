## Context

Mission mode replaces the routed dashboard, so `RailsBoard`/`SpecsBoard`/`RailRow` (with `RailPrDecisionStrip` + `AgentRuntimeRuns`) are never mounted. What the mission does have: inline/pinned `AgentPrDecisionCard` fed by `agent_pr_decision` envelopes (a `system` `agent_messages` row updated in place), `spec-draft`/`problem-frame`/`options` fenced blocks rendered as cards by `AgentMessage`, `JobDetailModal` + `useRuntimeRuns` (job-scoped), the context palette (`#` specs/jobs, `@` projects/files, `/` actions incl. `/launch rail`), and MCP `specrails_rails(launch|list|stop|…)`.

Verified gaps (2026-09-18): (1) the shared-cwd launch path (`isolationUnavailable = 'no-git'|'no-commits'`) never receives `originConversationId`, so no delivery row and no card; (2) `discarded` swallows `statusDetail` (gated on `deliveryBlocked`), `implementation_failed` offers only Discard; (3) no WS event writes into the conversation or starts a turn — the agent learns of failures only by polling; (4) `/agent-runtime/runs` (resume/recover/approve/settle/dismiss) is absent from MCP; (5) rails are not a palette entity.

Constraints: no specrails-core change; the mobile wire contract and `rail_pr_deliveries` state machine stay untouched (`decision` values are frozen — older clients drop unknown decisions); tier ladder semantics: a card button is a USER action (like PR-card buttons), an agent MCP call is subject to the tier; honest metrics (no invented state); i18n ×8.

## Goals / Non-Goals

Goals: one mission-native object per launch covering propose → launch → run → settle, editable before Play, present with or without git, honest about failure, actionable for recovery, and visible to the agent (state + trigger) so "why did it fail / resume it" works in chat.
Non-goals: a Board/Rails pane in the workspace rail (dropped); replacing the PR-decision state machine; agent-initiated conversations beyond ONE bounded failure turn; batch fan-out (`launch_all`) cards in v1; Builder milestone chains (they keep `MilestoneProgressCard`).

## Decisions

- **Proposal transport = fenced `rail-launch` JSON block**, not a tool call. Rationale: identical to `spec-draft` (parser pair server/client, last-valid-wins, streaming tail cut, fence promotion tolerance for local engines). Shape: `{ version:1, railIndex?: number|null, newRail?: { name }, ticketIds:number[], mode:'implement'|'batch'|'freestyle'|'loop', loopId?, aiEngine?, model?, reasoning_effort?, profileName?, targetPrNumber?, baseBranch?, rationale? }`. Unknown keys dropped; invalid block → rejected list surfaced as a muted "proposal unreadable" note (never silent). Alternative rejected: agent calls `specrails_rails(launch)` with `dryRun` — puts the card behind a tool round-trip and couples proposal to tier gating.
- **Card is client-resolved against live data.** The card fetches rails (`GET /rails`, free/busy + pending-decision state), tickets, detected providers/models (`useProviderDetection`, `GET /default-spec-model?provider=`), profiles and loops, and reconciles the proposal: an unknown rail → "new rail" mode; a busy rail → warning pill + rail switch; a stale model → adapter default (fail-open, same rule as `resolveLoopRoleEngine`). Selectors reuse `RailEngineSelector`, `RailProfileSelector`, `RailTargetPrSelector`, the loop picker and `AgentToolbarSelector` for model/effort.
- **Play = client POST, origin-tagged.** `POST /rails` (when new) then `PUT /rails/:i/tickets|engine|profile|name` then `POST /rails/:i/launch { originConversationId, originSurface:'agent-chat', loopId, model, reasoning_effort, profileName, targetPrNumber, baseBranch }`. 409s (`tickets_in_flight`, `pr_decision_pending`, `rail_limit_reached`) render inline on the card with the server's action text. Alternative rejected: Play sends a chat message "launch it" — reintroduces prose and a paid agent turn.
- **Persisted launch intent on the message row.** New nullable `agent_messages.intent` JSON (desktop-db migration; precedent `blueprint_messages.intent`): `{ kind:'rail-launch', status:'launched'|'dismissed', launchedAt, railIndex, runIds, prDeliveryId? , edited: <final config> }`. Set by `PATCH /api/agent/conversations/:id/messages/:mid/intent` after a successful launch. A taken proposal renders as a frozen "Launched → Rail N" stub linking to the run card; on reload nothing is editable twice.
- **Run card = generalized envelope, not a new card family.** `PrDecisionCardEnvelope` gains optional `runIds[]`, `railIndex`, `phase: 'proposal'|'launched'|'running'|'settled'|'delivery'`, `runtime: { status, currentStep, canResume, recoverableSteps, pendingApproval, failure: { code, detail, stepId } }`. Shared-cwd launches post a card too (`postPrDecisionCard` is reached from the shared-cwd branch of `rails-router.ts` with `prDeliveryId: null` and the loop run ids) and are updated from `onLoopRunFinished`/`onJobFinished`. `AgentPrDecisionCard` renders the delivery phase exactly as today; earlier phases render the run header (status pill, live elapsed, `phase · activity` line reusing `job-run-model.ts`, log chips → `JobDetailModal`, Stop) and, on failure, `statusDetail` + failure code + the runtime actions (Resume / Recover & retry / Approve / Relaunch / Discard) wired through `useRuntimeRuns` and the existing decision endpoint. Pinning: `phase !== 'settled-terminal'` keeps the card in the dock; a discarded/merged card unpins as today.
- **Failure trigger.** One server chokepoint `notifyMissionRunFailure(ctx, { runId, railIndex, originConversationId, reason, detail, stepId, recovery })` called from the settle paths on `failed|stalled|provider_limit` outcomes and from `stuck-run-detector` (once per episode). It (a) updates the envelope (`updatePrDecisionCard`), (b) inserts a `system` row `{ kind:'run-failure', … }` rendered as a compact failure marker, (c) enqueues ONE automatic agent turn via `AgentChatManager` with a fixed briefing (`agent-failure-briefing.ts`: run/rail/tickets, failure code+detail, last verify tail if harvested, the recovery options the runtime exposes, instruction "explain in ≤ 6 lines, propose the next action through the card, never relaunch by yourself"). Guards: skipped when the conversation is streaming (queued instead, dedup by runId), at most one auto-turn per run, provider/model of the conversation, accounted in `agent_invocations` like any turn, kill switch `SPECRAILS_MISSION_FAILURE_TURN=false` (card + system row still happen). Untagged launches (no origin) notify nothing.
- **MCP.** `specrails_jobs` gains `runtime_runs`, `runtime_evidence`, `runtime_resume`, `runtime_recover`, `runtime_approve`, `runtime_settle`, `runtime_dismiss` (tiers: reads `read`, mutations `ai-spawn` for resume/recover, `write` for approve/settle/dismiss). `specrails_rails(list)` adds `availability: free|busy|pending_decision|on_review` per rail. Operator prompt: propose via card; direct `launch` only on explicit "launch now"; after a failure turn, act only on user confirmation.
- **Palette.** `@rail-N` (`AgentContextKind` += `rail`) from `GET /rails`, chip tone `accent-warning`, serialized in `buildAgentContextBlock` as `rail N (name, tickets, state)`; `#` unchanged.
- **UX language.** Card chrome = `AgentPrDecisionCard`/`AgentSpecDraftCard` conventions (glass surface, header row with rail + `#` chips + status pill, `motion` enter/phase transitions, `AnimatePresence` on unpin, reduced-motion safe), consistent iconography (Play = `Play`, running = pulse dot, failure = destructive pill), disabled-in-flight buttons reconciled to the broadcast (no optimistic state). i18n keys under `agent:railCard.*` ×8 with the parity test.

## Risks / Trade-offs

- Agent emits malformed/partial blocks (small local models) → tolerant parser + fence promotion + visible "unreadable" note, and a Play-less fallback that still lists the intent as text.
- Card config drifts from server truth (rail got busy meanwhile) → Play always re-validates server-side; 409 rendered inline, card stays editable.
- Auto failure turn costs tokens / annoys → one turn per run, short fixed briefing, kill switch, never chains, queued behind a live turn.
- Envelope growth breaks older clients → all new fields optional; `decision` vocabulary untouched; mobile translation layer ignores unknown fields.
- Shared-cwd runs have no delivery row → card is keyed on `runIds`; delivery phase simply absent with an honest "no PR phase (no git)" note.
- Two sources of runtime truth (envelope snapshot vs `useRuntimeRuns` live) → envelope carries the settle-time snapshot only; the card polls `useRuntimeRuns` while running and prefers live data.

## Migration Plan

Additive DB migration (`agent_messages.intent`), additive envelope fields, new MCP actions, new fence type. Feature flags: `VITE_FEATURE_MISSION_RAIL_CARDS` / `SPECRAILS_MISSION_RAIL_CARDS` (default on; off ⇒ prompt reverts to today's launch verbs, fence ignored, no run-phase rendering) and `SPECRAILS_MISSION_FAILURE_TURN`. Rollback = flags off; persisted intents are inert.

## Open Questions

- Should `launch_all`/batch proposals render one card per rail or one grouped card? (v1: one per rail, agent emits N blocks.)
- Should the automatic failure turn also fire for `on_review` with a `pr_failed` push (delivery failure, not implementation)? (Leaning yes — same trigger, different briefing.)
- Rail creation from the card when `MAX_RAILS` is reached: show the cap error only, or offer "reuse an idle rail"? (v1: show cap + rail switch.)

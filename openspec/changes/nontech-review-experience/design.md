# Design — nontech-review-experience

## Context

Three trust cliffs for non-technical users: illegible progress (raw CLI logs), a git-vocabulary decision moment at `on_review`, and expensive revisions. The open `safe-pr-workflow` change carries the unimplemented SHALL ("plain-language what-changed + proof bundle; SHALL NOT expose raw git vocabulary") that Wave 2 discharges.

This design is grounded in a 10-agent verification pass (2026-07-27) that corrected the original framework. Verified facts this design builds on (do not re-litigate — file refs were checked against source):

- **Generation model is the law.** Every follow-up launch creates a NEW delivery row (`createPrDeliveryGeneration`), CAS-marks the predecessor `superseded`, keeps lineage via `supersedes_delivery_id`, enforces one-active-generation per rail (migration 48 partial unique index), and restores the predecessor if the new generation's build fails. Same-row mutation ("`revising` state") is refuted.
- **Wire hazard.** `coerceRailPrStateSnapshot` (client/src/lib/pr-delivery.ts:118) returns null for ANY unknown decision value — a stale client's PR card VANISHES, it does not degrade. Mobile `hub.*` wire contract is frozen.
- **`targetPrNumber` is post-PR only.** `resolveExplicitPrTarget` hard-requires an existing OPEN GitHub PR; at `on_review` `pr_url`/`pr_number` are null. The shipped continuation machinery (and the 409 guard's sole exemption, `prDeliveryContinuesTickets`) only activates at `pr_draft`/`pr_ready` with a real PR + EXACT ticket-set equality. Post-PR one-sentence revisions already work end-to-end (the operator prompt teaches them); the ONLY missing door is a revision launched AT `on_review`.
- **Branch, not session, carries the work.** Same-ticket branch resume is shipped (`rail_worktrees` ledger; an existing branch for the same ticket is reused, not suffixed). Claude sessions are cwd-scoped; `jobs.session_id` is last-non-null-wins (holds the FINAL step's session — verify/reviewer, not developer); the loop engine deliberately drops sessions at loop-backs. Every shipped recovery path chooses fresh-seed over resume.
- **Worktree lifetime.** Fresh reviewable worktrees STAY MOUNTED at `on_review` until the decision (inline comment rail-isolated-launch.ts:1532-1534); they are released at create-pr success and at continuation settles. Evidence harvest must run at settle while the worktree is mounted regardless.
- **No structured test results exist.** `loop_step_end.exitCode` is null BY CONTRACT for ai-steps; the PR body's Tests section is file PATHS only; the only verdict is the `VERIFICATION: PASS/FAIL` text sentinel (regex precedent: `rail-merge-orchestrator.ts:118`) which the Loop Decider itself distrusts.
- **`confidence-score.json` is shipped and unread.** sr-reviewer (core ≥4.12) non-optionally writes `openspec/changes/<name>/confidence-score.json` (schema_version 1, overall 0-100, five aspect scores, notes, flags[], documented 50-69 "recommend human review" band) into the worktree. Zero desktop code reads it. `openspec/**` is the repo-committed carve-out, so it also survives on the branch.
- **Narration substrate is free.** `loop_step` events carry kind/title/iteration + the RENDERED prompt (2000-char cap); the `events` table persists every raw provider JSONL line verbatim; `GET /jobs/:id` returns full history. Tool-result events are claude-only. `useOsNotifications` (done/failed) already ships; per-step activity checkpoints (`updateLoopStepActivityCheckpoint`) exist unwired.
- **Sync machinery is ready for a third surface.** ONE semantic derivation (`derivePrDeliveryPresentation`), ONE broadcast (`toRailPrStateMessage`), CAS + durable operation lease, authoritative POST-response snapshot.
- **Decision surface reality.** 12 decision states, 9 actions, orthogonal outcome/status axes, `no_changes` with its own verbs, partial N-of-M batches, recovery family — ~14 presentation states the human verbs must map.

## Goals / Non-Goals

**Goals:**
- Discharge the safe-pr-workflow plain-language review SHALL: a non-technical user can understand, judge, and decide on a delivery without git vocabulary.
- Make "request changes" a one-sentence action riding the shipped generation model, with version lineage and Back-to-v1.
- Make progress legible at three altitudes (glance chips → deterministic plain-language milestones → raw logs) with zero model cost and full provider parity.
- Honesty as a hard constraint: every displayed claim has a structural source and a labeled epistemic tier; no invented ETAs, counts, or verdicts.
- Cost-informed consent: dollars visible per cycle, before and after.

**Non-Goals:**
- Screenshots or live preview (user decision; "Open preview" for web projects is a named follow-up candidate).
- LLM-generated narration or packet prose (v1 is fully deterministic; a budget-capped Haiku catch-up digest is a future change if templates test insufficient).
- New chat surface / `chat_conversations` kind ("ask the packet" routes into agent chat).
- specrails-core changes (structured test counts + delta-scoped verification are a parallel, non-blocking core ask).
- New decision enum values or WS message shapes (wire-compat).
- Per-ticket revision of a batch subset (v1 revisions carry the full ticket set).

## Decisions

**D1 — Sequencing: packet first (Wave 2 after Wave 1 foundations), revisions + narration after.** Trust is won at the decision moment; non-tech users don't watch 25-40-min runs — they return on the (already shipped) done notification and land on the packet, which also physically hosts the revision input and the narration digest. Alternative (narration first) rejected: nicer waiting doesn't fix the trust cliff.

**D2 — Eager deterministic evidence harvest at settle.** In the settle path (before any worktree release), read from the mounted worktree: `confidence-score.json` (each unit's openspec change dir; tolerate absence), the `VERIFICATION` sentinel (reuse the existing regex precedent), and the verify step's output tail (bounded, e.g. last 4KB). Persist onto the delivery row (new JSON columns, additive migration). Alternative (parse at packet-render time) rejected: worktree may be gone, logs are unbounded, and render-time model parsing violates the honesty rule.

**D3 — Spec snapshot at launch.** Capture ticket title + description (and labels) onto the delivery row at INSERT (launch). "What you asked" renders the snapshot, never the live store (which can be edited mid-run — verified: `loadPrTicketData` resolves live). Small additive column; reuse at create-pr time too.

**D4 — Proof tiers by epistemic source.** The packet's "How it was checked" section renders three visually distinct tiers: (1) APP-VERIFIED — diff stats, files touched (incl. "no test files changed"), decider routed decision, shell exit codes where present; (2) AI-REPORTED — sentinel verdict + verify tail, always labeled "the AI reports its verification passed; Specrails did not independently run these tests"; (3) REVIEWER SCORE — confidence overall + aspect bars + flags, labeled "the AI reviewer's own confidence", with the 50-69 band surfacing "human review recommended". A numeric test count NEVER renders until a structured source exists (core ask). Alternative (prose narration of logs) rejected: launders self-report into verified claims.

**D5 — One server-side packet composer, existing surfaces.** A pure module composes the packet from durable data only (delivery row + harvested evidence + spec snapshot + `file_story_contributions` stats + `units[]` + cost from `run_ids`). Rendered as: (a) a routed full-screen page under ProjectLayout (JobDetailPage precedent — sidesteps the z-order ladder), (b) an expanded section of the existing agent-chat PR card. Both consume `useRailPrDecisions().act()` + `rail.pr_state` + the authoritative POST-response snapshot — no optimistic state, no new sync channel. "Ask the packet" = a button that opens agent chat with the delivery pinned (existing `origin_conversation_id` linkage; the add-desktop-agent-chat context-palette follow-up is the long-term plumbing). Alternative (new standalone surface + dedicated chat kind) rejected: surface proliferation, two Q&A brains diverge.

**D6 — Human verbs as a presentation layer; ladder pre-resolution; merge-local never hides.** Accept / Request changes / Discard map over `derivePrDeliveryPresentation` for the clean `on_review` path only. Accept pre-resolves via shipped probes (offline `gh auth token`, remote detection — blueprint-commit preflight pattern): remote + authed gh → create-pr (+publish as the follow-on); remote-less → merge-local, ALWAYS behind a plain-language consequence confirm ("this writes the changes directly into your project; there is no separate review copy; cannot be undone"). The two merge-local 409 guards (`wrong_branch`/`dirty`) get plain-language actionable copy. Every recovery/partial/no_changes state keeps the existing strip verbatim behind a "fine control" disclosure. A verb→state mapping table over all presentation states is a deliverable BEFORE UI work. Alternative (silent auto-merge under Accept) rejected: collapses the two-persona review design into a non-technical merge authority.

**D7 — Packet family, failure as flagship.** Four variants: Success / Nothing-to-change (maps to shipped `no_changes` + Mark done/Refine verbs) / Partial ("N of M ready" from per-unit outcomes in `units[]`) / Failed (what was attempted, why it stopped in plain words, ONE primary next action). The failed packet is the highest-priority template — it is the moment the persona decides whether the product is trustworthy.

**D8 — Revisions are new superseding generations. No `revising` state.** A revision launch creates a new generation row via the existing `createPrDeliveryGeneration` path; packet versions ARE the `supersedes_delivery_id` chain; "Back to version 1" rides the shipped restore machinery; crash-restore inherited. A nullable `revision_note` (the user's sentence) + `revision_of` column on the NEW row records intent — never a new decision enum member (D8 exists because of the verified vanish-card wire hazard). The strip's existing `iteratingPr` presentation covers the in-flight look.

**D9 — The on_review revision door: guard exemption.** `rails-router.ts` (and the duplicated logic in `server/mcp/tools/rails.ts`) learn ONE new exemption: a launch flagged as a revision of the rail's active delivery, carrying EXACTLY the delivery's full ticket set, is allowed while decision='on_review'. Batch revisions therefore always carry the full set; the packet states plainly "this revision may touch all N changes". Precedent for the return edge: `on_review` is already re-enterable (`rerouteFromStalePr`); precedent for the entry point: `SpecCard.allowOnReviewDrag` already ships.

**D10 — Fresh-seed sessions as the contract; resume opportunistic only.** The revision run seeds a fresh session from durable context: spec snapshot + canonical PR-body digest + branch diff summary + harvested evidence + the revision sentence. `--resume` of the prior session MAY be attempted as an optimization only when the recorded `worktree_path` still exists and the provider resume succeeds, with the Contract Refine one-time-fresh fallback wired from day one. Correctness never depends on session memory (matches the codebase's own recovery philosophy: loop-back session drops, contract-refine fresh retry, agent-chat auto-heal).

**D11 — A first-class factory `revision` loop, used by BOTH revision doors.** A fourth factory loop (next to implement/batch/freestyle), desktop-only, Architect-less: (1) a distilled revision command ai-step whose goal is the sentence + injected durable context, whose instructions ALSO orchestrate a reviewer pass — the `sr-*` agents are already present in the worktree via the overlay, so the step instructs spawning `sr-reviewer` over the resulting diff to produce `confidence-score.json`, exactly how `{{cmd:implement}}`'s markdown orchestrates sub-agents (zero core changes); (2) the standard `{{cmd:verify}}` step (full-scope verify — delta-scoping arrives only when the core delta-verification work lands; verification scope is never silently narrowed). The loop is orthogonal to the launch door: at `on_review` it enters via the D9 guard exemption; at `pr_draft`/`pr_ready` it rides the shipped continuation machinery — REPLACING today's full-implement relaunch (Architect included) as the taught path for "modify this delivery/PR" asks. If a run cannot produce the reviewer score, packet v2's reviewer tier degrades honestly to "not available" (D4). `classifyLoopEffect` flows the loop through isolated launch unchanged. NO duration promise anywhere; the percentile range (D14) renders once n≥5 revision runs exist, nothing before.

**D11b — The operator agent selects the revision loop itself.** `specrails_rails(launch)` gains explicit revision params (`revisionOfDeliveryId`, `revisionNote`); the operator prompt is taught: a user asking for modifications on an existing delivery or PR routes to the factory `revision` loop with those params (both doors), never to a full implement relaunch. The packet's revision input and the board's `allowOnReviewDrag` path use the same loop. Alternative (leave loop choice to the rail's stored mode) rejected: the stored mode is implement — every one-sentence tweak would silently pay the full pipeline.

**D12 — Drift-driven reshape nudges, advisory only.** Nudge toward reshaping the spec when (a) cumulative revision cost > 50% of the original build cost, OR (b) a revision's churn lands majority-outside the original delivery's file set (from `file_story_contributions`), OR (c) revision count ≥3 as a backstop. Banner with honest numbers; never a hard block; log which trigger fired. Failed revision renders an explicit packet: "Your change could not be applied — version 1 is still what's on review", sentence preserved for retry.

**D13 — Narration v1 is deterministic i18n templates.** A third altitude behind the shipped Story|Log toggle pattern in JobDetailPage/JobDetailModal: milestones templated from `loop_step` (kind, title, iteration, rendered command), `loop_step_end` (duration, decider verdict, Interrupted-when-missing), and tool events (file paths/commands from the persisted raw lines). All providers (loop events are provider-agnostic; tool granularity degrades predictably where adapters give less). Zero model calls, zero hallucination risk, rides the existing i18n pipeline (×8 parity test). Handles: plain jobs (raw parsed lines only), loop jobs (+ step boundaries), legacy runs without `loop_graph`, interrupted steps. Alternative (Haiku live narration) rejected for v1: progress-theater risk (activity ≠ progress), 8-locale generation cost, claude-only tool-results, and the prior product decision that the operator agent must not narrate.

**D14 — Honest duration ranges + stuck push.** One percentile endpoint (p25/p75) over `loop_runs.total_duration_ms` keyed by loop id (and `jobs.duration_ms` by command shape), rendered only when n≥5 — below that, nothing (honest-metrics memory). "Stuck" notification: server-side staleness threshold over the per-step activity checkpoints broadcasts a project-scoped event feeding the existing `useOsNotifications` path.

**D15 — Cost transparency.** Packet shows per-cycle cost ("This build cost $2.84" / "v2 revision: +$0.61", `~` marker for partly-estimated, `—` until authoritative) reusing `sumInvocationCostForRuns`; cumulative across the generation chain; expected-cost line next to the revision input once percentile data exists. No projected costs, ever.

**D16 — Flags and conventions.** `SPECRAILS_REVIEW_PACKET` / `VITE_FEATURE_REVIEW_PACKET` (default ON, opt-out, house pattern) gating Wave 2 surfaces; Wave 3 revision door behind `SPECRAILS_DELIVERY_REVISIONS`; narration behind `VITE_FEATURE_NARRATED_PROGRESS`. i18n ×8 with key-parity, semantic theme tokens only, coverage gates (80% server, 80% client lines/statements) are non-negotiable.

## Risks / Trade-offs

- [Stale-client card vanish if any new decision value leaks] → D8 forbids new decision enum members entirely; revisions serialize as existing values (`building` on the new generation, `superseded` on the old).
- [`confidence-score.json` absent (factory runs without an openspec change, older cores)] → harvest degrades tier-3 to "not available"; packet renders sentinel + decider verdict tiers; never blocks settle. Harvest failures are logged, non-fatal (same degradation philosophy as the overlay).
- [Sentinel is self-reported and could be gamed/wrong] → it is always labeled AI-REPORTED (D4); the packet never upgrades it to a verified claim. Core structured counts are the real fix (parallel ask).
- [Guard exemption could append to an undecided delivery unexpectedly] → exemption requires the explicit revision flag + exact full ticket set + rail's active delivery match; MCP copy updated in the same change; operator prompt taught the same rule.
- [Batch attribution: `file_story_contributions` attributes to the primary ticket only] → packet documents per-file attribution as delivery-level, not per-ticket, for batches (known limitation, stated honestly).
- [Worktree released before harvest on some paths (continuation settles)] → harvest runs INSIDE the settle path before any release call; for continuation settles the branch carries `openspec/**` as fallback source.
- [Percentiles misleading with sparse/bimodal data] → n≥5 floor, p25-p75 band (not a point estimate), keyed per loop id.
- [Deterministic narration too dry] → accepted v1 trade-off; the named follow-up (budget-capped Haiku catch-up digest, cached per (jobId, step, seq-range), own `ALLOWED_SURFACES` value) ships only if user testing demands it.
- [Merge-local plain-language confirm adds friction to remote-less flows] → deliberate: irreversible write into the user's checkout must never be one reflex click.
- [Scope: Wave 2 client surface is large vs coverage gates] → packet composer is a pure server module (cheap to test exhaustively); client page consumes precomputed data (presentational tests + the verb-mapping table as a unit-tested pure function).

## Migration Plan

1. **Wave 1** (additive migrations + server-only): evidence columns + spec-snapshot columns on `rail_pr_deliveries`; harvest wired into settle; percentile endpoint; stuck broadcast + client notification. No UI dependency; shippable silently.
2. **Wave 2** (flag-gated): packet composer + routed page + agent-card section + verb layer. Strip remains untouched underneath (fine-control disclosure embeds it) — rollback = flag off, byte-identical legacy decision UX.
3. **Wave 3** (flag-gated): revision door (guard exemption + revision loop + lineage UX) then narration altitude. Rollback per-flag; migrations are additive and harmless when unused.
4. **Parallel (non-blocking)**: core ask — structured test counts in `confidence-score.json` + delta-scoped verification. When counts land, tier-2 upgrades to tier-1 automatically (composer checks for the structured field).

## Open Questions

- "Open preview" (worktree + dev server + shipped native browser) for web projects: revisit after Wave 2 ships — the same worktree-lifecycle decision unlocks it and richer revision affordances.
- Does the packet page fully replace the strip's on_review actions long-term, or coexist permanently? (v1: coexist; packet is the canonical door for `on_review`.)
- Funnel instrumentation (spec→launch→settle→decide→accept) and the "simple launch" one-button path: recommended companions, tracked outside this change.
- Exact staleness threshold for "stuck" (initial: no step activity for 2× the step's p75, floor 10 min) — tune from data.

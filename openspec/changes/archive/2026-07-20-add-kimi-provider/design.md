## Context

Desktop has a provider registry and adapter contract, but the contract is optimized for spawning a CLI and parsing JSONL, and many product surfaces still contain explicit Claude/Codex/Gemini lists or Claude-only gates. This change intentionally targets Kimi's headless CLI (`kimi -p --output-format stream-json`) rather than Kimi Server. That choice matches the existing process lifecycle and avoids bundling or supervising a daemon.

Kimi's stream contains assistant messages, tool messages, retry/meta records,
and a successful terminal `session.resume_hint`; it does not provide Claude's
complete result/cost envelope. The integration must expose truthful
capabilities. “First-class” means provider-neutral execution wherever the
transport satisfies the feature contract, not unconditional exposure of
unsafe pure-output surfaces.

## Goals / Non-Goals

**Goals:**

- Register and discover Kimi like every other bundled provider.
- Support Kimi across setup, projects, autonomous chat/Explore/proposals,
  Quick Launcher, rails/loops without a Decider, profiles/manual roles,
  MCP/integrations, terminal, attachments, and analytics.
- Use the Kimi framework generated by Core and preserve relocated-workspace behavior.
- Normalize Kimi JSONL without misclassifying success, errors, tools, or session hints.
- Keep existing providers behaviorally unchanged.
- Represent unavailable native cost and first-turn cancel/resume limitations honestly.

**Non-Goals:**

- Starting or bundling Kimi Server.
- Implementing ACP.
- Storing Kimi credentials.
- Claiming native USD cost or OTEL support.
- Mirroring Claude's marketplace catalog.
- Emulating a no-tools/read-only boundary with prompt wording.
- Enabling Kimi for pure-output transforms before its verified headless
  transport can enforce their policy.

## Decisions

### Implement Kimi through the existing process adapter

`KimiAdapter` builds `kimi -m <model> -p <prompt> --output-format stream-json`,
uses one bound `--session=<id>` argument for known resumes, folds system
instructions into the prompt where required, and parses each JSONL object
tolerantly. Session ids share Core's 128-character safe grammar so an
upstream value can never be reinterpreted as another option. Existing process
cancellation/tree-kill remains the lifecycle boundary.

Kimi 0.27's interactive TUI and ACP frontends intercept `/skill:<name>` and
call `Session.activateSkill()`, whereas the print runner passes `-p` directly
to `session.prompt()`. Desktop therefore materializes project skills before a
headless spawn: it resolves only a safe direct child under
`.kimi-code/skills/`, strips frontmatter, applies Kimi-compatible argument and
skill-directory substitutions, and wraps the body in the same
`<kimi-skill-loaded>` activation prompt shape. Missing/unsafe skills fail
closed. This preserves the daemon-free CLI design without delegating workflow
selection to model inference. A known resumed session supplies
`${KIMI_SESSION_ID}`; a fresh session cannot, because Kimi creates the ID
inside print mode and emits it only at the end, so a skill that requires that
placeholder is rejected before spawn. Generated SpecRails skills do not use
it. Host materialization intentionally does not claim Kimi's private
`skill.activated` telemetry/origin event; matching those internal events would
require the SDK/ACP/server path rather than `-p`.

Alternative considered: REST/WS Server. Deferred because it would require daemon ownership, ports, bearer-token handling, reconnection, and a second provider runtime abstraction.

### Expose capabilities rather than provider-ID gates

Kimi advertises native resume after a known ID, native JSONL, reasoning effort
for K3 only, image-via-file support, project MCP, and no native
cost/OTEL/persistent stdin. UI and managers consume capabilities. Structured
actions are capability-gated rather than inferred from a provider ID.

Kimi does not advertise a hard `none`/read-only tool policy. Quick Spec, AI
Edit, Contract Refine, SMASH/Re-SMASH, Project Builder blueprint/milestone
generation, Loop Decider, file summaries, construction-story AI, and Agent
Studio generation/test/refine therefore fail closed without spawning. AI
auto-title takes the deterministic fallback. Capability checks precede all
destructive mutations, notably Re-SMASH child deletion.

Project Chat, Agent Chat, Explore/proposals, Quick Launcher, rails, and loop
AI/shell steps are deliberately agentic surfaces; Kimi uses its native
automatic prompt-mode permission posture there. Project Builder may target
Kimi during commit and launch committed tickets through a Kimi Batch rail, but
its pure blueprint/milestone generator may not select Kimi.

### Treat successful resume hints as terminal metadata

The adapter normalizes assistant/tool/meta records and derives a result from accumulated events. A `session.resume_hint` supplies `session_id`; process exit supplies success/failure. A cancelled first turn without a hint remains non-resumable, is recorded as aborted, and never receives a synthetic session ID.

### Use provider-aware model and effort catalogs

The static fallback catalog contains official Kimi IDs (`k3`,
`kimi-for-coding`, `kimi-for-coding-highspeed`). Only `k3` and its normalized
`kimi-code/k3` alias expose low/high/max; switching to another model clears
persisted K3 effort. Unknown providers never fall back to Claude models.
Profiles retain exact Kimi identifiers.

### Delegate rail semantics to Core

Desktop invokes the Kimi workflow skills generated by the minimum compatible
Core release. Queue, worktree, retry, batch, PR, and state ownership remain in
existing SpecRails managers. Kimi's built-in subagents are not treated as
SpecRails custom roles. Role skills remain direct children of
`.kimi-code/skills/` because Kimi's stable skill discovery does not scan an
unmarked nested catalog. Headless Core commands and role subprocesses inject
those skill bodies rather than forwarding a literal `/skill:` string. Custom
loops are allowed only when their graph does not contain a pure-output Loop
Decider.

### Make integrations additive

Kimi MCP uses `.kimi-code/mcp.json`; Serena and the Desktop MCP bridge merge
their entries without replacing user configuration. Integration installation,
health, verification, repair, removal, and job snapshots are keyed by effective
provider so mixed projects cannot leak Claude/Kimi state. Plugin feature
parity means SpecRails-managed integrations, not a copy of Claude Marketplace.

## Risks / Trade-offs

- **Cancel before resume hint loses the new session ID** → Record a truthful abort and offer a fresh retry.
- **No native cost envelope** → Store cost as null/unavailable and never convert zero placeholders into authoritative spend.
- **Prompt mode auto-permission differs from Claude flags** → Disclose that
  general Kimi prompt surfaces use Kimi's native autonomous policy and fail
  closed for every action whose no-tools/read-only boundary cannot be
  represented. Do not mutate the user's global Kimi config or claim prompt
  wording is a sandbox.
- **Experimental v2 may change the qualified stream/permission contract** →
  Remove `KIMI_CODE_EXPERIMENTAL_FLAG` from Desktop-owned child environments
  and qualify the stable Kimi 0.27 v1 engine only.
- **Print mode does not execute interactive slash commands** → Materialize the
  installed skill with upstream-compatible placeholders/envelope at the
  execution cwd, unit-test every spawn boundary, and fail before spawn on
  missing/unsafe files.
- **Kimi is not installed in CI or this workspace** → Version official contract fixtures, unit-test argv/parser exhaustively, and document a live canary release gate.
- **Large cross-cutting UI surface** → Replace local provider lists systematically and add inventory tests so future surfaces cannot silently omit Kimi.
- **Core/Desktop version skew** → Gate Kimi setup on the Core release containing `.kimi-code` rendering and show an actionable update.
- **Complete Windows prompts exceed native argv limits** → Transparently unwrap
  the standard npm `kimi.cmd`/`.bat` entry and transport the prompt through
  stdin. Reject an oversized native `.exe` before spawn with npm-install
  remediation; never truncate a workflow or invoke a user-controlled shell
  command.

## Migration Plan

1. Merge and publish Core Kimi support.
2. Merge Desktop adapter and hidden capability registration.
3. Enable Kimi in setup and project selection only when both CLI and compatible Core are available.
4. Existing project rows remain unchanged. New/re-registered projects may select Kimi alone or together with other providers; provider membership remains immutable after project creation under Desktop's existing lifecycle.
5. Rollback removes Kimi from Desktop selection but leaves user Kimi CLI/configuration untouched.

## MODIFIED Requirements

### Requirement: Canonical rich Builder spec contract
Every detailed spec generated by Project Builder SHALL contain a `kind` (`scaffold|feature|verification`), an English action-oriented title, a one-sentence `shortSummary` no longer than 240 characters, a `description` with exactly the five canonical named sections `## Problem Statement`, `## Proposed Solution`, `## Out of Scope`, `## Technical Considerations`, and `## Estimated Complexity` in that order, a separate `acceptanceCriteria` array containing 6–10 non-empty testable outcomes each at least 20 characters long, a valid `priority`, labels, and an optional dependency on an earlier spec. The Problem Statement SHALL be at least 200 characters, the Proposed Solution at least 500 characters and carry `###` sub-blocks (user experience, data model, interfaces & contracts, planned modules, key decisions), `Out of Scope` SHALL contain at least 3 bullets and `Technical Considerations` at least 5 bullets. The description SHALL NOT duplicate an `## Acceptance Criteria` section.

#### Scenario: Complete rich spec
- **WHEN** the Builder produces a detailed spec
- **THEN** its description explains the user problem in narrative form, the solution as a journey with UX, data, contract, module and decision sub-blocks, deliberate exclusions with their destination, labelled technical considerations, and a justified complexity, while its separate criteria cover the happy path, a failure case and automated verification

#### Scenario: Criteria are not duplicated
- **WHEN** a generated spec is materialized as a Board ticket
- **THEN** one deterministic `## Acceptance Criteria` section is folded into the stored description from the structured array

### Requirement: Phase-appropriate technical grounding
Day-0 M1 specs SHALL reference the selected stack, planned components, contracts, data shapes, risks, and inter-spec dependencies, labelling every module, path or contract they introduce as planned, and SHALL never claim that a repository path or identifier already exists. M2+ specs SHALL be grounded by reading the real project and SHALL name only existing paths and identifiers that were verified during generation.

#### Scenario: Day-0 scaffold has truthful context
- **WHEN** the first M1 spec describes project scaffolding before a repository exists
- **THEN** it names the chosen stack, notes that the repository already contains a README, defines run/test/CI outcomes, marks its module layout as planned, and does not claim unverifiable existing file paths

#### Scenario: M2 uses the real codebase
- **WHEN** a later milestone is generated for an existing project
- **THEN** its technical considerations refer to verified code locations and adapt the planned titles to the implementation that actually exists

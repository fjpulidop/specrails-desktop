## Why

The Blueprint "Launch Milestone 1" experience is broken end to end on a fresh Builder project: the launched jobs stay `running` for hours because factory loops disable the per-step watchdog and the loop's interactive step session arms no inactivity detector; the sidebar reads `0/8 done` after a delivery because progress counts only `done` while every ask-first delivery parks its specs at `on_review`; the "sequential" chain is a browser-local `localStorage` poller that dies with the window, never tells the user it is waiting, and bases chunk k+1 on the integration branch instead of chunk k's branch — so a greenfield walking skeleton rebuilds from an empty repo; and the milestone status never leaves `committed` because nothing writes `done`. A user hit exactly this (8 M1 specs, 3 launched, jobs running indefinitely, `0/8`), and the Builder is the first thing a new user touches, so this is the premium bar to fix now.

## What Changes

- **Loop step idle watchdog** (new). A loop AI step that produces no provider output for an inactivity threshold is torn down and settled as `stalled` instead of running forever; factory loops (which deliberately run untimed) get it by default; the step is retried ONCE by resume before failing; the `job.stuck` notification becomes actionable (the user can stop the step from the notification/job surfaces). Env-overridable, disableable.
- **Server-derived milestone progress** (new). `GET /:projectId/blueprint` returns, per milestone, live counts by spec state (`done`, `onReview`, `inProgress`, `todo`, `failed`), the milestone's active rails and PR deliveries, and a derived milestone state (`planned | committed | running | delivered | done`). A project-scoped `blueprint.milestone_progress` WS event fires on every relevant mutation so every surface updates without polling. When every spec of a milestone reaches `done`, the milestone is persisted as `done` in the blueprint pair and a completion event/toast fires.
- **Server-durable milestone launch chain** (new). The sequential launch plan moves from `localStorage` to a per-project SQLite table, advances inside `onLoopRunFinished` (no client polling), survives window close/app restart/machine sleep, is visible (chunk k/n, waiting, paused-by-failure, resumable), and **stacks**: chunk k+1's worktree is based on chunk k's delivered branch so the walking skeleton accumulates. Merging a later stacked delivery marks earlier ancestor deliveries merged (their specs → `done`). The client `MilestoneSequencerContext` and its `localStorage` keys are retired.
- **Premium milestone UI**. The Blueprint sidebar flyout (board + mission sidebars) and the Builder done screen render a segmented progress bar (done / in review / in progress / pending / failed), per-rail rows with their decision and a direct Review action, chain state, elapsed time, and honest copy ("3 of 8 delivered — in review" never "complete"). i18n ×8.
- The misleading `sequential.done` "complete" toast is replaced by state-accurate milestone toasts.
- **Premium spec generation** (new — the specs the Builder writes were noticeably thinner than the agent's super specs). ONE shared premium spec contract (`server/spec-contract-prompt.ts`) replaces the three divergent prompt texts (day-0 Builder, M2+ milestone generation, agent super-spec mode): narrative Problem Statement, a Proposed Solution with structured `###` sub-blocks (user journey, UX states, data model, interfaces & contracts, planned modules — explicitly labelled *planned* at day 0 — and key decisions), ≥3 Out-of-Scope bullets that say where the work lands, ≥5 labelled Technical Considerations (architecture, data & contracts, failure handling, security, performance, observability, testing strategy, dependencies, risks), a reasoned complexity, and 6–10 Given/When/Then-style acceptance criteria covering the happy path, at least one failure/edge case and automated verification. The deterministic quality gate (server + client mirror) raises its floors to match, so depth is enforced, not hoped for.
- **App-driven batched generation** (new — the structural reason specs were thin: 5–10 rich specs had to fit ONE response, so the model economised and the truncation repair told it to "tighten"). After approval the Builder emits an OUTLINE snapshot (every spec's kind/title/summary/priority/labels/dependency, empty bodies), then the app itself drives resumed continuation turns — two specs of full detail per turn, then one self-audit turn that sets `specsComplete` — keeping the panel live after every turn (`blueprint.done { continuing: true }`) and the generation progress honest ("Writing specs 3–4 of 8…"). Providers without native resume fall back to the single-response protocol.
- **Wave checkpoints** (new). A sequential milestone launch now carries `autoAdvance`: when off (the UI default), a rail that finishes successfully parks the chain at `awaiting_approval` with the next rail ready, and the user decides — **Launch next rail**, switch to **Continue automatically**, or **Cancel** — from the sidebar card, the Builder done screen and the toast; when on, the chain flows unattended exactly as before. The flag is toggleable while the chain runs (`PATCH /blueprint/chains/:id`).

## Capabilities

### New Capabilities
- `loop-step-idle-watchdog`: inactivity-based teardown + single resume retry for loop AI steps, actionable stuck notification, env contract.
- `milestone-progress`: server-derived per-milestone progress/state, WS event, milestone `done` persistence, premium progress surfaces.
- `milestone-launch-chain`: server-durable sequential milestone launch plan with stacked branches, visibility, resume, stacked-delivery merge convergence, and per-wave checkpoints (`autoAdvance` / `awaiting_approval`).
- `premium-spec-generation`: the shared premium spec contract, the app-driven batched generation protocol, and the raised deterministic quality floors, applied to day-0 Builder specs, M2+ milestone generation and agent super specs.

### Modified Capabilities
- `milestone-lifecycle`: "Launch Milestone 1 CTA" now delegates to the server chain (≤3 specs per rail, stacked); "Sidebar re-entry" progress semantics change from `done`-only counting to the full state breakdown, live over WS, and the milestone status advances to `done`.
- `loop-execution`: "Timeout And Crash Handling" gains the requirement that an untimed AI step is still bounded by inactivity.
- `blueprint-protocol`: "Canonical rich detailed-spec contract" adopts the premium depth (sub-blocks, ≥3 / ≥5 bullets, 6–10 criteria); "Single-response complete M1 generation" becomes app-driven batched generation (outline → detail turns → audit turn) with the single-response protocol kept only as the no-resume fallback.
- `project-builder-spec-quality`: "Canonical rich Builder spec contract" raises the gate floors; "Phase-appropriate technical grounding" allows explicitly-labelled *planned* artifacts at day 0 while still forbidding claims about existing paths.

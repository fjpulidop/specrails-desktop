# Design — loop-template-library

## Context

The Loop Builder (`loop-builder` change) already provides: a global loops store, the `LoopGraph` model + `validateLoopGraph`, the `aiLoopGraph` / `fixLoopGraph` template helpers, the `{{cmd:*}}` catalog with per-provider native invocation, the `{{const:*}}` library with two read-only built-ins (`VERIFICATION_PASS/FAIL`), and the `/loops` gallery that lists templates via `GET /api/loop-templates`. This change is **purely additive** on top of that surface: more templates, more commands, more discovery, one new constant. No schema, no engine, no provider-contract changes.

The structural reference for the port is a captured corpus of ~40 community loops (`.claude/loops-corpus.json`) — each entry has `{slug, title, description, category, tags[], kickoffPrompt, exitCondition{type,command,description,maxIterations}, guardrails[], steps[{name,prompt,shellCheck?}], triggerType, triggerConfig}`. The corpus is used **only** to drive coverage (which categories/patterns to represent, how many steps, what the exit goal is). All shipped prose is re-authored as Specrails-owned text — see "Ownership".

## Goals / Non-goals

**Goals**
- Grow the gallery to a categorised, searchable library of ~40+ Specrails-owned templates spanning the 15-value taxonomy.
- Make authoring DRY: distill the recurring step prose into reusable provider-aware `{{cmd:*}}` building blocks.
- Add a provider-aware `{{cmd:loop}}` so a template can delegate to the agent's own loop runner (`/loop` / `$goal`).
- Make every mutating template tamper-resistant via a single read-only `{{const:GUARDRAILS}}` contract.
- Keep the gallery usable at scale with search + category chips.

**Non-goals**
- No remote/community template registry, no user-submitted templates, no template import-by-URL. Bundled-only, like today.
- No new node types, no engine changes, no `triggerType` (hook/schedule) execution semantics — `triggerType` only informs which `{{cmd:*}}`/maxIterations a ported template uses; the engine still runs maxIterations-bounded loops.
- No DB migration. `GUARDRAILS` is a code built-in; templates/commands are code-bundled.

## Decision 1 — Category taxonomy as a closed 15-value set

Add `category: LoopCategory` to `LoopTemplate` (server) and `LoopTemplateSummary` (client). `LoopCategory` is a closed union over the 15 source categories:

```
API · Automation · CI · Database · Debugging · DevOps · Docs
Maintenance · Performance · Planning · Quality · Review · Security · Testing · Git
```

- Exported as `LOOP_CATEGORIES: readonly LoopCategory[]` from `loop-templates.ts` (single source of truth; the router and the client chip list derive from it).
- The 8 existing templates are categorised: `ship-and-green → CI`, `verify-pass → Testing`, `ci-watch → CI`, `lint-and-fix → Quality`, `type-safe → Quality`, `coverage-climb → Testing`, `build-fix → CI`, `deploy-check → DevOps`.
- The template payload (`GET /api/loop-templates`) adds `category` to each item. Optional on the wire (older clients ignore it); the client type marks it optional and falls back to no-badge when absent.
- A test asserts every template's `category` is a member of `LOOP_CATEGORIES` (no free-text drift).

## Decision 2 — A deterministic spec→graph porting transform

Templates are NOT hand-drawn graphs; they are generated by a helper so the 40 are consistent and all pass `validateLoopGraph`. Extend the existing builders rather than inventing a parallel path.

Each ported loop is expressed as a small **PortSpec** literal and compiled:

```ts
interface PortSpec {
  id: string; name: string; description: string;
  category: LoopCategory; tags: string[];
  steps: string[];        // AI-step prompts, already Specrails-authored (may embed {{cmd:*}}/{{const:*}}/{{spec.*}})
  goal: string;           // Decider goal — the exit condition, Specrails-authored
  maxIterations?: number; // from the source exitCondition; default 10
  loopBack?: 'last' | 'verify'; // which step the Decider 'continue' edge returns to
}
```

- `loopBack: 'verify'` ⇒ compile via the `fixLoopGraph` shape (main steps run once, then `verify → decider → fix → verify …`). Used for implement/verify/fix loops.
- `loopBack: 'last'` ⇒ compile via the `aiLoopGraph` shape (re-run the last step until the goal holds). Used for watch/poll/audit loops.
- The Decider goal is the loop's exit condition; where the goal is a green verification, it drags `{{const:VERIFICATION_PASS}}` so the sentinel stays in lock-step (existing convention).
- The compiled graph reuses the existing left-spine layout grammar (`COL_X`/`COL_RIGHT_X`/`ROW_GAP`) — no new layout code.

**`shellCheck` handling (cross-stack safety).** Source `steps[].shellCheck` is npm-specific (`npm test …`). Hardcoding it as a Shell node would break non-JS repos and contradicts the existing "agent detects the tooling" stance. So a step that had a `shellCheck` is authored to use the matching agent-driven magic command (`{{cmd:test}}`, `{{cmd:lint}}`, …) which detects the project's tooling at run time. The original command is, at most, offered as a parenthetical hint inside the prompt — never a hardcoded Shell node. Power users can still drop a Shell node manually after cloning.

**Guardrails injection.** Any step that mutates code/tests (implement/fix/refactor/upgrade) appends `{{const:GUARDRAILS}}` so the anti-gaming contract travels with the loop (Decision 4).

## Decision 3 — `{{cmd:loop}}` and the distilled common commands

Extend `LoopCommand` with one optional field:

```ts
/** Provider-native invocation prefix, keyed by ProviderId. When present it wins
 *  over coreCommand/native/template for providers it lists; providers not listed
 *  fall back to `template`. */
providerNative?: Record<string, string>
```

`expandCommands()` resolution order becomes: `coreCommand` → `native` → **`providerNative[provider]` (else `template`)** → `template`. (i.e. `providerNative` is consulted before the plain `template`, using `template` as the fallback for unlisted providers.)

- **`{{cmd:loop}}`** — `{ name:'loop', providerNative:{ claude:'/loop', codex:'$goal' }, template:'<autonomous-loop preamble>' , ticketScope:'per-ticket' }`. Expands to `/loop` on Claude, `$goal` on Codex, and a self-contained "Keep iterating autonomously until the goal below is met; re-check after every change and stop when it holds." preamble on Gemini/others. The author writes the goal text after the token (e.g. `{{cmd:loop}} keep the suite green for {{spec.title}}`). It is NOT `claudeOnly` — the fallback keeps it portable.
- **Distilled common commands** (all `template` kind, provider-invariant, `per-ticket` scope unless noted), each a short Specrails-authored prompt that (a) tells the agent to detect the project's tooling, (b) do the one job, (c) for the mutating ones, embed `{{const:GUARDRAILS}}` and end with the verdict sentinel where a loop reads it:
  - `test`, `lint`, `typecheck`, `build`, `coverage`, `format` — detect-and-run-and-fix the corresponding gate.
  - `commit`, `push` — git hygiene (no secrets; clear message; current branch).
  - `pr` — open/update a PR via the repo's tooling (`gh`), summarising the change (`all` scope — one PR for the rail's tickets).
  - `ci-status` — poll CI on the PR/branch via the repo's tooling and report green/failing (used by watch loops).
  - `audit` — run the dependency/security audit and fix high/critical findings one at a time with re-verification.
  - `docs-sync` — find docs affected by the change (README/API refs/inline) and update them to match.
  - `review` — self-review the working diff for correctness + quality and fix what is found.

These are append-only additions to `LOOP_COMMANDS`; they automatically surface as builder palette chips (the palette fetches `GET /api/loops/commands`). `dominantTicketScope` / `referencesClaudeOnlyCommand` keep working unchanged (no new `claudeOnly` command is added; `loop` is portable).

## Decision 4 — `{{const:GUARDRAILS}}` as a read-only built-in

Add to `BUILTIN_CONSTANTS` (read-only, like the verify sentinels):

```
GUARDRAILS = the canonical hardened anti-gaming block (multi-line string):
  - Do not modify the check command or exit criteria to force success.
  - Do not skip, disable, or bypass checks to satisfy the exit condition.
  - Do not weaken, delete, or skip tests; do not replace real assertions with always-pass tests.
  - Prefer fixing production code over patching tests to go green.
  - If stuck after several iterations, stop and report the blockers instead of gaming metrics.
```

- It is a **built-in** (not a seeded `loop_constants` row) so it is read-only, cannot be deleted, and needs no migration — it renders with the 🔒 lock chip in the palette exactly like `VERIFICATION_PASS`.
- `resolveConstants` already resolves built-ins first, so `{{const:GUARDRAILS}}` works at run time with zero engine change.
- Rationale for read-only: the guardrails are a tamper-resistance contract; an editable guardrails constant could be weakened to defeat its own purpose. (A future change MAY add an editable `EXTRA_GUARDRAILS` seeded constant if users want to extend them — out of scope here.)

## Decision 5 — Discovery UI: search + category chips

In `LoopsPage`, the Templates section gains a filter header above the grid:

- **Search input** — debounced (~150ms); case-insensitive substring match over `name + description + tags.join(' ') + category`. Pure function `filterTemplates(templates, { query, categories })` lives in a testable module (`client/src/lib/loop-template-filter.ts`).
- **Category chips** — one chip per category that actually appears in the catalog, each showing a count; multi-select (OR within categories, AND with the search query); an "All" affordance clears the category selection. Chips use semantic theme tokens (`accent-*`, `surface`, `muted`) — no brand-named colours.
- **Card badge** — each template card renders its category as a small badge plus its tags (tags currently only show in the preview modal).
- **Empty state** — when the active filter yields zero templates, a localized "no results" row with a clear-filters action.
- Filtering is **client-only** over the already-fetched template list (no new endpoint). The user's own loops (Drafts/Published) are NOT filtered by this — the filter scopes to the Templates section only.
- Filter state MAY persist to `localStorage['specrails-desktop:loop-template-filter']` (last query + selected categories) for return visits; persistence is best-effort and never blocks render.

## Ownership (hard constraint)

Consistent with the `loop-builder` proposal ("Specrails-owned text and naming … no third-party content is bundled"): every template `name`, `description`, step `prompt`, and Decider `goal` is **re-authored** in original Specrails phrasing. The corpus supplies structure (category, tag set, step count, exit-condition intent) only. Generic descriptive nouns that are unavoidable for a pattern (e.g. "lint", "coverage", "flaky test") are fine; verbatim sentences from the source are not. The implementation MUST NOT copy source prose into the bundle.

## Risks / trade-offs

- **Template-count assertions in tests.** `loop-templates.test.ts` hardcodes expected ids; adding ~32 templates requires updating those assertions. Mitigated by switching the assertion to "every template has a valid category + non-empty tags + a graph that passes `validateLoopGraph` + exactly one terminal Decider branch pair", plus a `>= 40` count floor, instead of an exhaustive id list.
- **Palette crowding.** ~13 new command chips + existing ones can crowd the inspector palette. Acceptable for v1; a future grouping/scroll affordance is out of scope.
- **`providerNative` precedence bug surface.** The new resolution branch must not regress existing `coreCommand`/`native`/`template` commands — covered by keeping their precedence first and adding dedicated expansion tests for `loop` across claude/codex/gemini.
- **i18n drift.** 15 `categories.*` keys + `gallery.*` keys × 8 locales is the bulk of the surface; the key-parity test is the backstop.

## Migration / rollback

- No DB migration. Rollback = revert the code; the `loops` table, seeded constants, and existing templates are untouched.
- The feature inherits the existing `FEATURE_LOOPS_SECTION` / `SPECRAILS_LOOPS_SECTION` flags — turning Loops off hides the whole surface including the new catalog.

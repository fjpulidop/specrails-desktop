# データの保存場所

手短に言うと、**Specrails はあなたのリポジトリをきれいなまま保ちます。** アプリをいずれかのプロジェクトに向けても、そこに住み着いたり、設定ファイルをあちこちに散らかしたり、頼んでいないものを勝手に書き換えたりはしません。あなたのコードはあなたのもののまま、きれいに保たれます。

## リポジトリはきれいなまま

Specrails 自身のファイル — データベース、プロジェクト別の状態、エージェント定義、設定、テレメトリ、要約、その他動作に必要なすべて — は、ホームディレクトリ配下の、すっきりまとまった 1 か所に置かれます。

```
~/.specrails/
```

**設定 ▸ 情報** には、データベースの正確な場所と、使用中のアプリのバージョンが表示されます。

このフォルダがアプリのプライベートなワークスペースです。プロジェクトレジストリ、プロジェクト別のデータベース、同梱ツール、運用に関わる細々したものはすべてここに置かれます。あなたの実際のコードリポジトリが、これらの置き場として使われることは決してありません。

つまり、こういうことです。

- リポジトリの `.gitignore` がアプリによって書き換えられることは **ありません**。
- リポジトリがツールの設定ファイルや隠しの状態ディレクトリで散らかることはありません。
- Specrails からプロジェクトを削除しても、コードの中に散らかったものが残ることはありません。

これまで、プロジェクトのあちこちにフォルダやファイルをこっそり追加するツールを使ってきた方にとって、これは意図的な方針転換です。Specrails は、リポジトリに向けて使い始めても、そのリポジトリの git 履歴にとっては **何も起きていないのと同じ** になるように作られています。

## 唯一コミットされるもの — それも意図的に

意図的な例外がちょうど 1 つだけあります。そしてそれこそがこのツールの核心です。**あなたの OpenSpec スペック** です。

スペックはあなたのリポジトリの中、次の場所に置かれます。

```
openspec/
```

これは意図的なものです。スペックは **成果物** です。何を作ると決めたのか、なぜそう決めたのかを、バージョン管理され、レビュー可能な形で記録したものです。スペックはコードの隣にあるべきもので、git で追跡され、プルリクエストで見え、チームで共有されます。それこそが価値です。スペックは使い捨ての一時的な状態ではなく、プロジェクトの歴史の一部なのです。

ですからルールはシンプルで、正直です。

- **`openspec/`** → リポジトリに置かれ、コミットされます。意図的にそうしています。
- **Specrails が必要とするその他すべて** → `~/.specrails/` 配下に置かれ、あなたの邪魔をしません。

## なぜこの仕組みなのか

Specrails は AI ツール群を自身のプライベートなワークスペース（`~/.specrails/` 配下）から実行し、本当に触れる必要があるもの — あなたのコードを読むこと、そして頼まれたスペックを書くこと — のためにだけ、あなたの実際のリポジトリに手を伸ばします。ツール群、フレームワーク定義、各種の記録は、すべてアプリのホームフォルダにとどまります。

あなたにとっての結論はこうです。プロジェクトを追加し、パイプラインを実行し、スペックを探求し、いろいろ試してみても、リポジトリの作業ツリーと git 履歴が変わるのは、あなたが予想できる範囲だけ — つまりコミットしたスペックと、パイプラインが書いたコードだけ、という安心感を持てます。それ以外のものが紛れ込むことはありません。

## プロジェクトを削除する

Specrails からプロジェクトを削除すると、アプリは `~/.specrails/` 配下にある自身のプロジェクト別の状態を片付けます。すでにリポジトリにコミットされたスペックは、本来あるべき場所 — あなたのリポジトリの中 — にそのまま残ります。それらはあなたのものだからです。

## ディスクに残っている実行用ワークツリー {#retained-worktrees}

Rail の各実行は、`~/.specrails/projects/<プロジェクト>/worktrees/` の下にある専用の Git ワークツリーで作業します。実行が完了すると Specrails はそのワークツリーを削除しますが、何も失われないと証明できる場合に限ります。証明できない場合（未コミットの変更、そこにしかないファイル、削除の失敗など）はワークツリーを残すため、時間とともにたまっていきます。

**設定 ▸ ストレージ** に、全プロジェクトのワークツリーが一覧表示されます。ステータスバーの **アプリのリソース** ポップオーバーからも開けます。各ワークツリーには、サイズ（バックグラウンドで計測）、未使用の期間、PR、削除すると失われるものが表示されます。

- **失うものなし**：未コミットの変更がなく、無視ファイルはすべて再生成できる（`node_modules`）か、リンクか、メインのチェックアウトにある同じファイルと同一です（コピーした `.env` など）。ブランチのコミットはすべてリモートか別のブランチにあるか、デリバリーがマージ済みです。
- **あなたの判断待ち**：まだあなたの対応が必要です。理由はそれぞれ表示されます。未コミットの変更、そこにしかない無視ファイル、このブランチにしかないコミット、判断待ちのデリバリー、直近の操作（1 時間以内）、Git で確認できなかった、のいずれかです。Git で確認できないワークツリーは、クリーンとは見なされません。

ワークツリーを選んで **削除** を押します。確認画面には、空く容量とブランチの扱いが表示されます。

- ブランチは既定で **残る** ため、コミットは引き続き利用できます。
- **新しい内容のないブランチも削除する** を選ぶと、失うものがないブランチだけが、Specrails が確認したコミットを指したままの場合に限り削除されます。

未コミットの変更や、そこにしかないファイルがあるワークツリーは選択できません。先にコミット、コピー、または破棄してください。Intent セッションに属するワークツリーは一覧に表示されますが、操作はそのセッションから行います。各ワークツリーは削除の直前に再確認されます。確認後に何か変わっていれば残され、結果にその理由が表示されます。削除したワークツリーで動いていたプロセス（開発サーバーなど）は停止されます。

## PR の外に保管されたファイル {#safety-archives}

実行中、Specrails はワークツリーにいくつか自分のファイルを追加します。プロジェクトの指示（`CLAUDE.md`）、安全フックを含むローカル設定、コマンドやスキルへのリンクです。これらが PR に入ることはありません。ワークツリーを削除するとき、書き込んだときのままであれば Specrails はこれらを削除するので、通常の実行では何も残りません。

どれかが変更されていた場合（たとえばエージェントが `CLAUDE.md` を編集した場合）や、Specrails 自身のファイルだと証明できない場合は削除しません。ワークツリーの隣のフォルダ（`<worktree>.specrails-overlay-quarantine-…`）へ移し、PR カードに **PR に含まれなかったファイルを N 件保管しました** と表示します。

- **詳細**: フォルダ（**パスをコピー** と **Finder で表示** 付き）と、保管された各ファイルのサイズを表示します。
- **削除**: フォルダ名とファイル数を示して確認したうえで、そのフォルダだけを削除します。
- **閉じる**: 通知を隠します。ファイルはそのまま残ります。

**設定 ▸ ストレージ ▸ PR の外に保管されたファイル** には、全プロジェクトのこうしたフォルダがサイズと経過日数付きで一覧表示されます。複数選んでまとめて削除できます。Specrails が削除するのは、そのプロジェクトのワークツリー領域内にあるこの名前のフォルダだけで、外へのリンクをたどることはありません。

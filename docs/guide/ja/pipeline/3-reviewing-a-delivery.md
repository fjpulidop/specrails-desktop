# アプリ内で納品をレビューする {#review-a-delivery}

レビュー待ちの納品には 2 つの表示があります。**概要**（結論、根拠、判断ボタン）と**変更**（納品が実際に何を変えたか）です。納品の**レビュー**ボタンからレビューを開き、**変更**を選びます。

## 変更を読む

左のファイル一覧には、変更された各ファイルの状態（追加、変更、削除、名前変更）、`+` と `−` の行数、確認済みにしたときのチェックが表示されます。右の差分は 1 ファイルずつ読み込まれるため、大きな変更でも軽快です。**統合**と**並べて表示**のレイアウトを切り替えられ、Specrails は選択を記憶します。非常に大きなファイルは先頭の行を表示し、**ファイル全体の差分を読み込む**で続きを読み込めます。バイナリファイルはバイナリとして表示されます。

変更は、納品がベースブランチから分岐した地点から測定されるため、その後ベースに入った内容は表示されません。納品にまとめたブランチがまだない場合は、どのスペックのブランチを読むか選べます。

## コードに対するレビュアーのメモ

レビュアーの指摘、示されたリスク、実行が解決するために起動されたレビューコメントは、対象の行の下に表示されます。ファイルも行も示していないメモはファイル一覧の上に並ぶため、何も隠れません。古い納品や、場所を示さなかったレビュアーの指摘は、この一覧に表示されます。

## エージェントに変更を依頼する

行番号をクリックして行を選び（Shift クリックで範囲を広げます）、**エージェントに変更を依頼**を選んで変更内容を書きます。Specrails はファイル、行範囲、選択したコードとともに、レビューフィードバックとしてスペックに保存し、スペックへのリンク付きのメッセージを表示します。そのスペックの次回の実行に反映されます。すぐ実行するには、概要の**変更を依頼**を使います。ここには人同士のコメントスレッドはありません。チームとの議論は GitHub で行ってください。

## エディターで開く

**エディターで開く**は、選択した行でファイルを VS Code、Cursor、または JetBrains IDE で開きます。エディターは**設定 → コード → エディター**で選べます。ファイルはお使いのプロジェクトのチェックアウトから開かれ、レビュー対象のブランチがそこでチェックアウトされていない場合があります。

## マージ前にコンフリクトを確認する {#merge-preview}

あなたを待っている各デリバリーは、チェックアウトに触れずに、ベースブランチの**現在の状態**（最後に fetch した `origin/<base>`）と比較されます。Git は両者をメモリ上でマージし、リポジトリには何も書き込みません。rail カード、レビューパケット、ライブボードには次のように表示されます。

- **… で main とコンフリクトします**：変更はもうきれいにマージできません。ファイルが一覧されます。警告の見た目で表示されます。
- **Rail N と … で衝突します**：同じベースで待っている別のデリバリーが同じ行を変更しているため、後からマージする方がコンフリクトします。
- **このブランチの作成後、main は N コミット進みました**：ベースが進んでいます。判断する前にブランチの更新を検討してください。
- **すでに main に含まれています**：変更はすでに取り込まれています（squash マージの後など）。

プレビューは、デリバリーの状態が変わったときや run が終わったときに更新されます。Specrails が複数の結果を自分でマージし戻すときは、きれいに適用できるものから先にマージします。Git 2.38 以降が必要です。古い Git ではプレビューが利用できないと表示されます。

## 納品物をどうするか選ぶ {#pr-decision}

完了した実行が尋ねるのは一つだけ、その結果をどうするかです。カードには次のステップ（PR の作成、公開、確認）のメインボタンが一つあり、その隣の **レビュー** で分かりやすいレビューパケットを開けます。そのほかの操作は **その他の操作** にまとめられています。

- **ブランチをチェックアウト** はブランチをプロジェクトフォルダーに置き、試せるようにします。
- **ローカルに統合** は、このコンピューター上で結果をベースブランチにマージします。GitHub は不要で、事前に確認が入ります。
- **破棄** は結果とそのブランチを削除します。事前に確認が入ります。

操作が失敗すると、通知で何ができなかったかが示され、**再試行** を選べます。

## Specrails に PR をグリーンに保たせる {#pr-ci}

ミッションから PR を作成すると、会話に **PR #N の CI を監視して修正** が表示されます。これは任意で、勝手に始まることはありません。**開始** を選ぶと、Specrails は PR のチェックを待ち、失敗したものを修正し、ベースブランチをマージしてコンフリクトを解決し、あなたのコンピューター上で結果を確認してから、チェックがグリーンになるまで同じ PR に修正をプッシュします。進行は実行ストリップで追えます（「CI を待機中」「失敗したチェックを修正中」「修正を PR にプッシュ中」）。

強制プッシュ、ブランチの書き換え、チェックを弱めることは一切せず、PR の公開、マージ、クローズも行いません。これらの判断は常にあなたのものです。完了できない場合（チェックが失敗し続ける、必須のチェックが報告されない、あなたしか用意できないシークレットが必要など）は、停止して理由を伝えます。**今はしない** を選ぶと、この納品ではこの提案が非表示になります。あとで PR カードまたはレールの **その他の操作** にある **CI / コンフリクトを修正** から開始できます。

## キーボード

| キー | 操作 |
| --- | --- |
| `j` / `k` | 次 / 前の変更ファイル |
| `n` / `p` | 次 / 前のレビュアーのメモ |
| `v` | ファイルを確認済みにする |

入力欄に入力している間、これらのキーは無視されます。確認済みの印はあなただけのものです。後のリビジョンでファイルが変わると**確認後に変更されました**と表示され、再び未確認として数えられます。

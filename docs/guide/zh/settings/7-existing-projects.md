# 在现有项目中工作

这些功能帮助运行尊重已经存在的项目：规格不涵盖的内容、架构师在规划前的问题、测试真正证明了哪些需求、在修改旧代码前如何描述它，以及团队已经写下的规则。每项功能都需要支持它的 specrails-core 版本；在此之前，其开关显示为灰色，并提示更新 Core。

## 不在范围内

每个规格都可以列出它有意**不**更改的内容。Quick 和 Explore 会为你填写；在规格窗口中，它显示在描述下方的 **不在范围内**，每行一项，可以像其他字段一样编辑。代理在每次启动时都会随规格一起收到它。

## Jira 中的架构师问题

在 **设置 ▸ 在现有项目中落地** 中打开 **将架构师的澄清问题发布到 Jira**。当运行因架构师需要答复而停止，或基于假设继续时，Specrails 会将其作为一条评论发布到关联的 Jira 问题。在 Jira 中回复该评论：回复会作为澄清添加到规格上，规格的下一次运行会读取它。你仍然可以在应用中答复已暂停的运行。

## 已证明的需求

当测试在标题中写明它所证明的需求（`[spec:<能力>/<需求>]`）时，评审页面会显示 **已证明的需求 X/Y**：哪些需求由通过的测试证明、哪些还没有测试、哪些是本次变更涉及的。分析页面按循环显示同样的信息。若要在变更的需求没有测试时让 CI 失败，请在测试之后添加 `specrails-core pipeline trace --check --tests-passed`。

循环库还提供 **偏差巡检**，这是一个只读循环，会比较每个规格的描述与代码的实际行为，并列出每处矛盾。它不做任何更改。

## 触及时建立基线

打开 **触及时建立基线** 后，当变更触及没有任何规格描述的代码时，会先描述这些代码：在未修改的代码上证明的当前行为测试，以及一份简短的现状规格。评审页面会显示 **在工作经过之处创建规格**，包括模块、需求和测试，其成本与变更分开显示。如果这些测试在未修改的代码上失败，运行会在编辑模块之前停止并说明原因。

## 项目规则

**设置 ▸ 项目规则** 列出项目已经运行的检查（lint、类型、测试、CI），以及写在 `CLAUDE.md` 或 `AGENTS.md` 等文件中的每条规则，并分为：

- **已执行**：已有检查保证它。
- **可自动化**：可以由检查保证。**创建规格** 一键将其变为规格。
- **仅限人工**：需要有人查看。它们会出现在每个评审页面的 **需要人工检查** 中。

Core 尚未能分类的规则（例如刚添加项目、盘点以离线方式运行时）显示为 **未分类**；配置提供方后点击 **重新盘点** 即可完成分类。

**重新盘点** 会刷新列表。当项目还没有验证命令时，Agent Runtime 设置会优先提供这些检查。

# 你的数据存放在哪里

一句话总结：**Specrails 始终让你的仓库保持纯净。**当你把应用指向你的某个项目时，它不会鸠占鹊巢，不会到处散落配置文件，也不会改写任何你没要求它改的东西。你的代码依然是你的，而且干干净净。

## 你的仓库保持洁净

Specrails 自身的文件——它的数据库、各项目状态、agent 定义、设置、遥测、摘要，以及运行所需的一切——都集中存放在你主目录下一个整洁的家中：

```
~/.specrails/
```

**设置 ▸ 关于** 会显示数据库的确切位置以及你正在运行的应用版本。

那个文件夹是应用的私有工作区。项目注册表、各项目数据库、内置工具链以及所有运行相关的零碎信息都住在这里。你真正的代码仓库绝不会被当作这些东西的「垃圾场」。

这意味着：

- 你仓库的 `.gitignore` **不会**被应用改写。
- 你的仓库不会被工具配置或隐藏的状态目录弄得乱七八糟。
- 从 Specrails 中移除一个项目，不会在你的代码里留下一地狼藉。

如果你以前用过那种悄悄在项目里到处添加文件夹和文件的工具，那么这是一次有意为之的不同选择。Specrails 的设计宗旨，就是让「把它指向某个仓库」对该仓库的 git 历史而言是一件**毫无波澜的小事**。

## 唯一**会被**提交的东西——这是有意设计

恰好有一个有意为之的例外，而它正是整个工具的意义所在：**你的 OpenSpec spec。**

spec 存放在你的仓库中，位于：

```
openspec/
```

这是刻意为之。你的 spec 是一份**交付物**——一份带版本、可审查的记录，记述了你决定构建什么以及为什么。它们理应与你的代码并肩而立，被 git 追踪，在 pull request 中可见，与团队共享。这正是其价值所在：spec 不是用完即弃的临时状态，而是你项目历史的一部分。

所以规则简单而坦诚：

- **`openspec/`** → 存放在你的仓库中，被提交，这是有意设计。
- **Specrails 所需的其他一切** → 存放在 `~/.specrails/` 下，不挡你的道。

## 为何如此设计

Specrails 在它自己的私有工作区（`~/.specrails/` 下）运行 AI 工具链，只有在确实需要触碰你真实仓库的事情上才会伸手进去——读取你的代码，以及写入你要求的 spec。工具链、框架定义和各种记账信息全都留在应用的家目录里。

对你而言，好处在于：你可以放心地添加项目、运行流水线、探索 spec、试验各种想法，因为你仓库的工作区和 git 历史只会以你预期的方式发生变化——你提交的 spec，以及你的流水线写出的代码。别的什么都不会偷偷溜进来。

## 移除一个项目

当你从 Specrails 中移除一个项目时，应用会清理它在 `~/.specrails/` 下自己的项目级状态。已经提交到你仓库的 spec 仍留在它们该在的地方——你的仓库里——因为它们是你的。

## 磁盘上保留的运行工作树 {#retained-worktrees}

每次 Rail 运行都在 `~/.specrails/projects/<项目>/worktrees/` 下的独立 Git 工作树中进行。运行结束时，Specrails 会删除该工作树，但前提是它能证明不会丢失任何内容。如果无法证明（有未提交的更改、只存在于那里的文件，或删除失败），就会保留该工作树。时间一长，这些工作树就会越积越多。

**设置 ▸ 存储** 会列出所有项目中保留的工作树。也可以从状态栏的 **应用资源** 弹出面板进入。每个工作树会显示其大小（在后台测量）、闲置时长、对应的 PR，以及移除后会丢失的内容：

- **无可丢失**：没有未提交的更改，每个被忽略的文件都可以重新生成（`node_modules`）、是链接，或与主检出中的同一文件完全相同（例如复制来的 `.env`）。其分支上的每个提交都已在远程仓库或其他分支上，或其交付已合并。
- **等你处理**：还有需要你处理的事项，每个原因都会列出：未提交的更改、只存在于那里的被忽略文件、只在此分支上的提交、仍在等待你决定的交付、最近的活动（过去一小时内），或 Git 无法检查它。Git 无法检查的工作树绝不会被视为干净。

选择工作树后点击 **移除**。确认窗口会显示可以释放多少磁盘空间，以及分支如何处理：

- 默认会 **保留** 分支，因此其提交仍然可用。
- 勾选 **同时删除没有新内容的分支** 后，只有无可丢失的分支才会被删除，并且仅当它仍指向 Specrails 检查过的提交时才会删除。

有未提交更改或只存在于那里的文件的工作树无法选择，请先提交、复制或丢弃这些内容。属于 Intent 会话的工作树会列出，但需要在其会话中处理。每个工作树在移除前都会再次检查：如果在你确认后有任何变化，它会被保留，结果中会说明原因。在已移除的工作树中仍在运行的进程（例如开发服务器）会被停止。

## 保留在 PR 之外的文件 {#safety-archives}

运行期间，Specrails 会向工作树添加一些它自己的文件：项目说明（`CLAUDE.md`）、带有安全钩子的本地设置，以及指向其命令和技能的链接。它们永远不会进入 PR。移除工作树时，如果这些文件与 Specrails 写入时完全一致，就会被删除，因此正常的运行不会留下任何东西。

如果其中某个文件被修改过（例如智能体编辑了 `CLAUDE.md`），或者 Specrails 无法证明某个文件是它自己的，它就不会删除，而是移到工作树旁边的文件夹（`<worktree>.specrails-overlay-quarantine-…`），PR 卡片上会显示 **已保留 N 个未进入 PR 的文件**：

- **详情**：显示该文件夹（可 **复制路径** 和 **在 Finder 中显示**）以及每个保留文件的大小。
- **删除**：先确认，说明文件夹名称和其中的文件数，然后只删除该文件夹。
- **忽略**：隐藏提示，文件保持原处。

**设置 ▸ 存储 ▸ 保留在 PR 之外的文件** 会列出所有项目中的这类文件夹及其大小和保留时长。可以多选后一次删除。Specrails 只会删除项目自身工作树区域内、名称完全符合的文件夹，并且从不跟随指向外部的链接。
